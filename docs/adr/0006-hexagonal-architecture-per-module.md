# 0006 - Hexagonal architecture (ports and adapters) per module

- Status: Accepted
- Date: 2026-08-23

## Context

ADR-0002 established domain-first vertical slices. The first slices were flat: `models`, `schemas`,
`repository`, and `router` files side by side, with the SQLAlchemy model doubling as the domain
object. That is fine for thin CRUD, but Vitae's core is about to grow real, framework-independent
domain logic (extraction, the agent loop, insight generation, similarity), and we want that logic
isolated from FastAPI and SQLAlchemy so it can be reasoned about and tested without infrastructure.
Mastering and demonstrating Clean Architecture is also an explicit goal of this portfolio.

## Decision

Each module is a hexagon under `src/vitae/modules/<domain>/`:

- `domain/` is framework-free (stdlib + typing only): frozen dataclass entities, enums, invariants,
  and repository interfaces as `typing.Protocol` ports.
- `application/` holds the use cases as a service that depends only on the domain ports and a
  `UnitOfWork` port. The service owns the transaction boundary (`uow.commit()`); it never imports a
  session.
- `infra/` holds the adapters: `repository/` (SQLAlchemy `<Entity>Model`, mappers, and the
  `Sql<Entity>Repository` that implements the port) and `http/` (FastAPI router plus Pydantic
  schemas). The router is the composition root that wires the concrete adapters into the service.

Dependencies point only inward (`infra -> application -> domain`, and infra implements the domain's
ports). The domain owns identity and time (the service generates `id` and `created_at`). Operational,
non-domain endpoints (`health`, `meta`) stay flat.

## Consequences

- The domain and application layers are unit-testable with fake ports and a fake UnitOfWork, no
  database and no HTTP. This is enforced by the `unit` test tier.
- Swapping an adapter (a different store, a second delivery mechanism) touches only `infra`; the
  domain and application layers do not change.
- The structure is uniform and generated by `scripts/new_domain`, so new modules start consistent.
- Cost: more files and a mapper per aggregate, and three representations of a concept (domain entity,
  ORM model, API schema) kept in sync. This is heaviest for trivial CRUD and pays off as a module
  gains real logic. We accept it deliberately.

## Alternatives considered

- Flat vertical slices (the previous approach). Rejected: the domain object was a SQLAlchemy model,
  so business logic could not exist independently of the framework, and the AI-heavy modules ahead
  need exactly that separation.
- Horizontal technical layers (`models/`, `services/` at the top). Already rejected in ADR-0002.
- Pragmatic hexagonal with the ORM model doubling as the domain entity (no mappers). Rejected: the
  domain would import SQLAlchemy, so it would not be truly framework-free, which is the whole point.
