## Q1 - Connection vs pool vs session, and why the session is per-request

### Question

The engine is created once at startup, but a new `AsyncSession` is opened per request. Explain the difference between connection, pool and session. Justify why the engine/pool lives for the whole app lifetime but the session is per-request. What breaks if you share a single global session across all requests?

### What I said

- Connection. A way to persist the connection with the database (circular definition).
- Pool. A way to manage several connections in parallel depending on the DB config. I think of it like threads the database can support. With the pool I can connect to several sessions in parallel.
- Session. The unit of work that groups the changes made through the ORM (entities, tables, views). On commit they all apply, and if something fails everything is rolled back, using transactions.
- Failure mode of a global session. It would be a bottleneck, because a single global connection is the limit.

### Feedback

The session part was good. Unit of work that groups changes and commits or rolls them back with transactions.

The connection definition was circular. Missing the concrete part. It is an authenticated TCP socket, expensive to open, and that cost is what justifies the pool.

You conflate session with connection. They are distinct layers. Many sessions can be alive. The pool lends them connections. The session is high-level Python. The connection is the socket.

You missed the failure mode. You said "bottleneck" (performance). The real problem with a global session is correctness, not speed.

### Correct answer

A connection is an open, authenticated TCP socket to Postgres. An OS and network resource. Opening it is expensive (TCP handshake, authentication, server-side session setup), on the order of milliseconds. That cost is why the pool exists.

A pool is a set of already-open connections reused across requests, instead of opening and closing one per query. It lives inside the engine. That is why the engine is created once in `lifespan` and shared via `app.state`. Opening the pool is paid once.

A session is SQLAlchemy's unit of work. It tracks the ORM objects you add or modify (identity map) and translates them to SQL. It borrows a connection from the pool when it executes and returns it when done. The transaction (atomic commit/rollback) is something the session uses, not the session itself.

Why the pool is global and the session is not. The pool is safe to share because it has no per-request mutable state and is internally synchronized to hand out connections. The session holds per-request mutable state (identity map, pending objects, an in-flight transaction), so sharing it creates data races.

What breaks with a global session. `AsyncSession` is not safe for concurrent use. It is meant for a single logical task at a time. With two concurrent requests sharing one session, two things go wrong.

They share a single connection, and a connection runs one statement at a time. asyncpg raises `InterfaceError: another operation is in progress`.

They share the identity map and pending objects. One request's `commit()` or `rollback()` drags along the other's half-done changes, and one user's data can appear in another's response. Data leak between users.

It is correctness, not performance. That is why the pattern is `async with sessionmaker()` per request. Each request gets its own isolated unit of work and returns the connection to the pool on close.

Follow-up. An object is safe to share globally if it has no shared mutable state. Immutable, or internally synchronized. The pool satisfies this. The session does not, because its identity map and in-flight transaction are mutable state of a single request.

### Common mistakes

Defining connection circularly.

Conflating session with transaction, or session with connection.

Explaining the global-session failure as a bottleneck (performance) instead of correctness.

## Q2 - Liveness vs readiness, and why to separate them

### Question

`/health/live` touches nothing and returns ok. `/health/ready` runs `SELECT 1` and returns 503 if the database fails.

1. Conceptual difference between liveness and readiness, and why it matters to separate them. Think about who consumes each endpoint and what action it takes.
2. If you merged them into a single `/health` that checks the database, what damaging behavior would it cause in production during a transient 30s database outage? Give the chain of events.

### What I said

Liveness. Whether the API is alive and able to serve requests. Readiness. Also checks the database or other critical infrastructure needed to serve.

If I merge them, the system considers the whole API to be failing and tries to restart it, when in reality only the database or a critical provider is failing. That is why it matters to separate what is not working, in order to take the right measure.

### Feedback

Part 1 correct. Part 2, you caught the core idea (restarting the API does not fix the database), but you missed the detail that makes merging them damaging. Each probe triggers a different action. A failing liveness probe means the orchestrator kills and restarts the pod (destructive). A failing readiness probe means it stops routing traffic to the pod but leaves it alive (reversible). The damage comes from attaching the destructive action (restart) to a condition a restart cannot fix.

### Correct answer

Liveness. The process is alive and not wedged. Consumed by the orchestrator (Kubernetes). If it fails, kill and restart the pod. Destructive. That is why it must be dependency-free. Only a genuinely wedged process warrants a restart.

Readiness. The pod can serve right now, including its critical dependencies (database). Consumed by the orchestrator or load balancer. If it fails, remove the pod from the traffic rotation but leave it running. Reversible. When the dependency returns, traffic resumes with no restart.

Damage chain if a single `/health` that checks the database is used as liveness, and the database drops for 30s.

1. The database drops. `/health` returns 503 on every pod at once (they share the database).
2. The orchestrator reads liveness-failing and kills and restarts every API pod at once.
3. Restarting the API does nothing for the database. The fresh pods still fail. Crash-loop, restart storm.
4. In-flight requests, warm connection pools, and in-memory state are lost. The mass reconnect when the database returns is a thundering herd that slows recovery.
5. Net. A benign 30s blip becomes a full, self-inflicted API outage, and the restart never touched the real fault.

Correct design (the one in the repo). Readiness checks the database, so a blip just de-pools the pods until the database answers, then traffic resumes with no restart. Liveness stays dependency-free.

Never attach a destructive recovery action (restart) to a condition a restart cannot fix (a dependency being down). That is why they are separate.

### Common mistakes

Explaining the failure only as "it thinks the API is failing and restarts it" without naming liveness=kill vs readiness=de-pool.

Not mentioning the crash-loop / restart storm or the loss of in-flight state.

## Q3 - Injected engine/session (app.state + Depends) vs a module-global engine

### Question

A session reaches a route through a chain. Engine and sessionmaker built in `lifespan`, stashed on `app.state`. `get_session_maker(request)` reads it off `request.app.state`. `get_session` yields an `AsyncSession`. Routes use `SessionDep`. The tutorial alternative is a module-level global. `engine = create_async_engine(os.environ["DATABASE_URL"])` at import time, imported wherever needed.

1. What concrete wins does the injected version give that the global does not?
2. Specifically for testing against a throwaway database, what goes wrong with the module global, and why does injection solve it?

### What I said

With DI you can switch the adapter as long as you respect the interface (e.g. swap Postgres for Mongo behind a repository) without changing business logic. You configure the connection in a single place. You can test with a mock repository/database because the concrete implementation is not hardcoded.

Correct in spirit but generic. Conflated the repository-swap layer with the engine-injection layer, and did not reach the concrete testing mechanism.

### Feedback

Part 1 mixed two different injection points. Swapping Postgres for Mongo behind an interface is the repository pattern, a different layer. The win at this layer is about the session/engine itself. Every route gets its session via `Depends(get_session)`, so you change what session they get (URL, pool size, a rollback-wrapped transaction) in one function, zero routes touched. Part 2 needed the concrete mechanism, which is all about when the engine line runs.

### Correct answer

Part 1. What injection buys at the engine/session layer. The route declares what it needs (a session), not where it comes from. Because the session arrives via `Depends(get_session)`, you can, without touching any route, point at a different DB URL, change pool size or timeouts, swap in a test engine, or wrap each request's session in a transaction that rolls back (the trick that isolates tests).

Part 2. The timing is the whole answer.

```python
# db.py, module top level
engine = create_async_engine(os.environ["DATABASE_URL"])   # runs at IMPORT time
```

Importing the app pulls this in transitively before any test runs.

```
test file -> from vitae.main import app -> routers -> db.py
          -> create_async_engine(os.environ["DATABASE_URL"])  # fires here, bound to whatever URL exists now
```

So the engine is already built and bound before the test starts. To point it at a test DB your only options are bad.

1. Set `DATABASE_URL` before the import. Now you fight import order, which is fragile in Python. One stray top-level import binds the engine to the wrong DB.
2. Monkeypatch `db.engine` after import. Reassigning a module global, hoping nothing captured the old reference. Brittle and order-dependent.

Two more problems sit on top of that.

3. Singleton. One engine for the whole process. Tests cannot each get their own isolated engine/DB state.
4. Async landmine. An async engine binds to the event loop it was created on. Created at import time, it latches onto that loop. `pytest-asyncio` makes a fresh loop per test, so queries fail with `RuntimeError: ... attached to a different loop`. Looks unrelated. Costs hours.

How injection fixes it. `create_async_engine(...)` runs inside `lifespan`, which fires at app startup, not import. The app is built by a factory `create_app(settings)`, so tests build the app with test settings (test `DATABASE_URL`), or override the seam.

```python
async def override_get_session():
    async with test_sessionmaker() as session:
        async with session.begin():   # everything this test does...
            yield session
            # ...rolls back on exit -> next test starts clean

app.dependency_overrides[get_session] = override_get_session
```

The engine is created when you decide, with the config you choose, as many times as you want. Nothing binds at import time, so nothing fights you.

A module-global engine binds config and event loop at import time, which you do not control. Injection moves that binding to startup time, which you do.

### TypeScript bridge

Version B is `export const db = connect(process.env.DATABASE_URL)` at a module top level (connects on first import, every test inherits that one connection). Version A is a NestJS provider, or a factory you pass config into (each test configures its own).

### Common mistakes

Answering only "you can mock it" (generic DI) without the import-time-binding mechanism.

Conflating repository-swap (adapter behind an interface) with engine/session injection.

Missing the singleton and event-loop consequences.
